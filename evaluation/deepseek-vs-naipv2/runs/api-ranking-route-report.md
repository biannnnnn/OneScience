# DeepSeek API 排序协议评测

评测日期：2026-08-25

## 结论

纯 API 路线中，当前最可行的协议不是绝对 0–100 打分，也不是单次 pairwise，而是：

```text
同一批论文做两次 listwise 排序
  → 第一次使用确定性原顺序
  → 第二次使用完全倒序
  → 对两次 rank 做 Borda 聚合
  → 只输出批内相对档位，不输出绝对质量分
```

在与产品默认一致的每批 4 篇设置下，双向 listwise Borda 的初始效果达到或超过本轮 NAIPv2 基线，同时运行间排序一致性较高。但样本仍只有 32 篇、48 个批内论文对，尚不足以直接发布。

## 协议对比

| 协议 | RTS 排序 | Accept 排序 | 主要问题 |
| --- | ---: | ---: | --- |
| 绝对 0–100 打分，batch=8 | 0.5714 | 0.5625 | 分数压缩，accept/reject 均分仅差 1.25 |
| 单次 listwise，batch=8，原序 | 0.5179 | 0.6875 | 输入顺序偏差明显 |
| 单次 listwise，batch=8，倒序 | 0.7768 | 0.8125 | 高 RTS 恰好位于前部，指标被位置偏差抬高 |
| 双向 listwise Borda，batch=8 | 0.6920 | 0.8281 | 接近 NAIPv2，但仍有 11.6% 聚合并列 |
| 单次 pairwise，原方向 | 0.6563 | 0.5000 | A 位置胜率 65.6% |
| 单次 pairwise，交换 A/B | 0.5000 | 0.4375 | A 位置胜率升至 81.3% |
| 双向 pairwise 一致性过滤 | 0.6471 | 0.4286 | 仅覆盖 53.1%，不可用 |
| NAIPv2，batch=4 同组比较 | 0.6875 | 0.8125 | 本轮小模型基线 |
| 双向 listwise Borda，batch=4，运行 1 | **0.7604** | **0.8594** | 当前最佳 API 协议 |
| 双向 listwise Borda，batch=4，运行 2 | **0.7292** | **0.8438** | 使用相同倒序结果和第二次原序结果 |

表中的 Borda 指标将聚合并列按 0.5 计分。batch=4 共 48 个 RTS 论文对和 32 个跨标签论文对。

## 位置偏差

### Listwise batch=8

- 原序与倒序输出的两两顺序一致率：59.82%；
- 原序输出遵循输入顺序：66.07%；
- 倒序输出遵循倒序输入：74.11%。

单次 listwise 不能直接使用。必须通过对称输入或其他位置随机化策略抵消顺序偏差。

### Pairwise

- 原方向与交换 A/B 后选择同一物理论文的比例：53.13%；
- 双向都同意时，RTS 准确率 64.71%；
- 双向都同意时，跨标签 accept 准确率 42.86%；
- 双向一致性过滤覆盖率只有 53.13%。

因此 pairwise 路线在当前 prompt 下淘汰。

## Batch=4 双向 Listwise

这组配置与产品默认 `n=3` 完全一致：一篇用户稿件加三篇近期参考论文。

第一次原序 + 第一次倒序的 Borda 聚合：

- RTS non-tie accuracy：79.07%；
- RTS tie-half accuracy：76.04%；
- Accept non-tie accuracy：89.66%；
- Accept tie-half accuracy：85.94%；
- 非并列覆盖率：89.58%；
- 与 NAIPv2 的非并列排序一致率：72.09%。

将原序请求重复一次后：

- 两次原序输出的两两顺序一致率：93.75%；
- 两次双向 Borda 结果一致率：95.83%；
- 第二组聚合 RTS tie-half accuracy：72.92%；
- 第二组聚合 Accept tie-half accuracy：84.38%。

说明 temperature=0 下运行间随机波动可控，主要风险来自输入位置，而双向 Borda 能显著缓解该问题。

## 时延和 Token

Batch=4、32 篇、8 个期刊批次：

- 原序 8 次请求：39.84 秒、11,761 tokens；
- 倒序 8 次请求：38.94 秒、11,719 tokens；
- 双向合计：78.79 秒、23,480 tokens；
- 平均每个期刊批次：约 9.85 秒、2,935 tokens；
- 默认 `k=5` 顺序执行估计：约 49 秒、14,675 tokens，共 10 次 API 请求。

后续可在保证限流的情况下并发 2–3 本期刊，将墙钟时间继续降低。

## 产品协议建议

不再展示 DeepSeek 的绝对 0–100 分，改为：

1. 构造 `[用户稿件, 参考1, 参考2, 参考3]` 的稳定顺序；
2. 发起一次 listwise 排序；
3. 将输入完全倒序，再发起一次相同 prompt；
4. 对每篇论文计算 `rank_original + rank_reversed`，和越小越强；
5. 用聚合 rank 比较稿件与三篇参考论文；
6. 稿件胜过 3 篇参考论文：高于近期基线；
7. 胜过 1–2 篇或出现聚合并列：接近近期基线；
8. 一篇都未胜过：低于近期基线。

界面应显示“批内相对排名”和两次排序是否一致，不再显示未经校准的绝对质量分。

## 发布前门槛

- 将固定测试扩大到至少 100 篇；
- 覆盖不少于 25 个默认 batch=4 期刊批次；
- 冻结 prompt 后重复运行至少 3 次；
- 双向聚合排序一致率不低于 90%；
- RTS/人工 pairwise accuracy 不低于 NAIPv2 对照；
- 结构化输出成功率达到 99% 以上；
- 完成限流、重试、单边成功时的降级策略和成本预算。
